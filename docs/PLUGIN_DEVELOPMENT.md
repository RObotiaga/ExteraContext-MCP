# Проверка разработки плагинов

Инструменты связывают поиск API с конкретной сборкой и отделяют завершение очереди от сохранности видео. Сервер проверяет источники и предоставленные свидетельства; исполнение Android-клиента и независимая runtime-аттестация остаются отдельными действиями.

## Получение APK без Telegram-входа

1. `list_client_releases(channel,before?,pages=1)` читает публичные объявления **exteraReleases** и **AyuGramReleases** через HTTPS `t.me/s`. До пяти страниц за вызов, без Telegram session, токенов, Authorization или cookie jar. Название, дата, объявленный размер и ссылка на сообщение образуют каталог. Вариант из имени файла помечен как предположение. Ссылка на сообщение не является ссылкой на байты APK.
2. `list_public_apk_mirrors(channel)` читает GitHub releases разрешённых репозиториев разработчиков: `exteraSquad/exteraGram`, `exteraSquad/exteraGram-Beta`, `AyuGram/AyuGram4A`. Старые и beta-сборки обозначены явно. Результат содержит asset ID, размер, URL и опубликованный digest, если он есть. Принадлежность репозитория разработчику не доказывает совпадение с Telegram-вложением или нужной установленной сборкой.
3. `download_client_apk(channel,repository,asset_id,expected_sha256?)` повторно получает описание выбранного asset из GitHub API и скачивает APK в новый файл `.cache/public-apks`. Произвольный URL не принимается. Размер, SHA-256 при наличии ожидаемого/опубликованного хеша и структура APK проверяются; при ошибке удаляется только собственный незавершённый файл. APK не устанавливается и не запускается.
4. Если нужной сборки нет на доступном зеркале, вызвать `request_client_apk(target,reason?)`. Клиент с поддержкой MCP form elicitation получает форму для **абсолютного локального пути**. Без этой возможности возвращается `USER_APK_REQUIRED` с просьбой прикрепить APK в чат или указать путь. MCP сам не загружает бинарное вложение: после получения файла агент передаёт доступный на хосте путь в `request_client_apk(target,path)`.

Просьба сохраняет требования клиента: package, versionCode, версия, SHA-256, ABI и вариант, если они известны. Переданная сборка проверяется через `inspect_client_apk`; несовпадение явно возвращается как `APK_MISMATCH`. Вариант full/lite не подтверждается только именем/версией, поэтому остаётся unbound до отдельного анализа. Ответы формы decline/cancel завершают вызов как `USER_DECLINED`/`USER_CANCELLED`, без повторной формы. Явный `path` позволяет сразу провести инспекцию.

Проверено 5 октября 2026: оба канала доступны как каталог; публичные превью не предоставили URL байтов документов. Из официального GitHub exteraGram анонимно скачан APK 9.6.6 (42996930 байт), SHA-256 `43f264dff803136f13b9e1eb7e98c7f8c61b7bae8b6f0f716d96535ec8ee7fb8`; инспекция подтвердила `com.exteragram.messenger`, versionCode 33625, arm64-v8a. Это историческая сборка. В `AyuGram/AyuGram4A` release assets не обнаружены. В такой ситуации нужен APK пользователя, а не подмена другой сборкой.

## Паспорт и поиск

`resolve_target` принимает прежние поля, а также `package`, `version_code`, `apk_sha256`, `android_api`, `abi`, `variant`, `sdk_origin`. Поля — заявление вызывающего: сверять их следует с APK и установленным клиентом. SDK requirement плагина не является фактической версией SDK.

Паспорт передаётся в `search_knowledge`, `find_api`, `find_usage`, `get_recipe`, `check_compatibility`. Для API, usages и recipes цель учитывается до ограничения выдачи; контекст конфликтов сохраняется отдельно. Пул кандидатов ограничен 500, превышение объявляется явно и не позволяет назвать совместимость подтверждённой. Версия без package, build и APK-хеша не считается точной сборкой. Противоположные утверждения об одном API в пересекающихся целях требуют проверки; разные версии сами по себе не образуют конфликт. Выдача без target сохраняет прежний формат с предупреждением.

`inspect_client_apk(path,class_name?)` вычисляет SHA-256, читает package/versionCode/versionName и ABI, по запросу извлекает DEX-класс. Требуются Android SDK apkanalyzer и Java. На Windows Java вызывается напрямую, без оболочки. Изменение файла во время инспекции отклоняется. SDK и установленный экземпляр приложения этим не проверяются.

## Артефакт, мост и влияние хука

`inspect_plugin_artifact(path)` читает EAF или standalone Python без исполнения, проверяет AST, архив, встроенный/архивный DEX и объявленный хеш. Возвращает artifact SHA-256, Python SHA-256, DEX SHA-256 и версию. Дубли имён и превышение размеров отклоняются. Предупреждения о `__file__` и `elyx.assets` требуют проверки загрузчиком клиента; они не доказывают ошибку установки.

`probe_bridge_contract()` готовит `.plugin` для штатного загрузчика целевого клиента. Проверяет отдельно настоящий `hook_utils.find_class` и Class reflection, int/long/boolean, поле `notify`, вызов Python dynamic_proxy **из Java**, before/after собственного View.setTag и независимость двух InMemoryDexClassLoader со статическим состоянием. Локальный хук снимается в finally. DEX содержит только небольшой `BridgeProbe.java`; его исходник и контрольные суммы поставляются в `scripts/fixtures/bridge-probe.json`. Плагин не читает переписки и не отправляет сообщения.

Генерация исходника всегда возвращает PENDING. `probe_bridge_contract(report)` оценивает предоставленный JSON, но не записывает runtime-verified факт. Фактический SDK не угадан из requirement: текущий probe оставляет его неизвестным, а полный результат — PENDING до отдельного достоверного измерения SDK. Подготовленный probe пока не исполнялся на физическом телефоне в рамках проверки MCP.

`analyze_hook_impact(path,class_name,method,callers)` показывает декларации и ссылки в явно перечисленных caller-классах точного APK, сохраняя перегрузки. Это частичное статическое покрытие; поток, порядок callbacks и полный call graph остаются неизвестными. Общий getter может обслуживать одновременно UI, рекордер и возобновление записи; его замену нельзя считать локальной правкой таймера.

## Журналы и приёмка функции

`inspect_media_packets(path)` через ffprobe измеряет реальные локальные video/audio пакеты: количество, first/max PTS и максимальный промежуток после сортировки PTS. SHA-256 до и после защищает от изменения файла. Требуется ffprobe; отсутствующая зависимость не превращается в PASS. Пакеты не доказывают движение изображения или слышимую речь.

`analyze_run(log,expected_artifact?)` принимает до 64000 UTF-8 байт JSONL и отделяет сессии, версии, поколения загрузки и задания. Отсутствующие/повреждённые seq и разрывы препятствуют приёмке. Сопоставляются все события загрузки с ожидаемыми version, Python/DEX/artifact SHA-256 и package/versionCode/APK SHA-256. Совпадение заявленных полей журнала не является независимым чтением установленного артефакта.

Аудиты `camera.source.audit`/`media.source.audit` содержат `expected_us`, фазу `camera_file`/`source_file` либо `saved_copy` и `measurement`: bytesBefore/After, tracks с mime, samples, firstPtsUs, maxPtsUs, maxGapUs. Проверяются начало и конец, промежутки, стабильность копии, номера/суммарная длительность частей и ACK. Допуск времени — 1 секунда, включая небольшой отрицательный PTS подготовки аудиокодера. Отсутствующий maxGapUs оставляет покрытие неизвестным. Поэтому прежние журналы могут доказать укороченную запись, но не полную непрерывность.

`verify_feature` возвращает FAIL при противоречии, PENDING при недостающих критериях, EVIDENCE_CONSISTENT при согласованности предоставленных данных. `runtime_verified` всегда false; `record_runtime_result` остаётся закрытым до доверенной аттестации.

- `long_round_camera`: источник camera, сохранность пакетов/копии/частей, ACK, идентичность артефакта и наблюдения движения, речи после минуты и непрерывности стыков.
- `import_round`: источник imported, такие же проверки медиаданных и идентичности, соответствие квадратной обрезки preview, звук, стыки и наблюдения маршрутов gallery/message/fallback. Камерный сценарий не подменяет импорт.

Таймер, hook.install.done, build/mock PASS и queue.done подтверждают только свои этапы. Например, 100 секунд на таймере при 60 секундах пакетов исходника дают FAIL независимо от успешной отправки.

## Проверки и ограничения доставки

Локальные Python/Node regression tests проверяют контракт MCP, форму запроса/отказ, противоположные API-утверждения, укороченную запись, пропущенные свидетельства и разделение сценариев. `mcp/test/development-live-smoke.mjs` — отдельный явный прогон: публичные каталоги и выбранные локальные APK/EAF/медиа. Он не запускается обычным `npm test` и не считается испытанием телефона.

После обновления checkout потребуется перезапуск подключения MCP, чтобы уже работающий процесс показал новые инструменты. Установка APK/плагина, фактическая версия SDK и проверка пользовательской функции на устройстве выполняются отдельно и обозначаются своим уровнем доказательств.
