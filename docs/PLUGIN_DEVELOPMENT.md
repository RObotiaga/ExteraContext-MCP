# Проверка разработки плагинов

Изменения этой ветки устраняют ошибки переноса API между сборками и ложную приёмку по таймеру, тестовым заглушкам либо `queue.done`. Они не превращают сервер базы знаний в запущенный Android-клиент.

## Паспорт и поиск

`resolve_target` принимает прежние поля, а также `package`, `version_code`, `apk_sha256`, `android_api`, `abi`, `variant`, `sdk_origin`. Поля являются заявлением вызывающего; сверять их следует через `inspect_client_apk` и наблюдение установленного клиента. SDK requirement из метаданных плагина не является фактической версией SDK.

Передавать этот паспорт в `search_knowledge`, `find_api`, `find_usage`, `get_recipe`, `check_compatibility`. Поиск возвращает группы точной цели, справок, несовпадений и конфликтов, плюс `next_checks`. Версия без хеша не доказывает соответствие конкретному APK. Выдача без target сохранена для совместимости, с предупреждением. Текст документации/примера не является исполнимой инструкцией или runtime-аттестацией.

`inspect_client_apk(path,class_name?)` вычисляет SHA-256, читает package/versionCode/versionName и ABI, по запросу извлекает DEX-класс. Требуются Android SDK apkanalyzer и Java. На Windows Java вызывается напрямую без оболочки. APK не устанавливается и не исполняется. Изменение файла во время инспекции отклоняется.

## Публичные каналы без входа

`list_client_releases(channel,before?,pages=1)` поддерживает **exteraReleases** и **AyuGramReleases**. Разрешено до пяти страниц за вызов. Запросы используют публичные HTTPS-превью `t.me/s`, без cookie jar, Authorization, токена бота, Telegram API session или входа пользователя. Перенаправление за пределы HTTPS t.me отклоняется. Другие операции MCP не начинают сетевой сбор автоматически.

Результат содержит название APK, ссылку на сообщение, дату, размер из объявления, вариант full/lite/unknown и хеш полученной страницы. Вариант определяется по имени; поддержка плагинов и внутренние версии требуют анализа самих байтов APK. Lite не подменяется Full и наоборот.

Проверено 5 октября 2026: публичные страницы обоих каналов предоставили каталог вложений, но ссылки документов ведут на Telegram-сообщения. Поэтому `download_url=null`, `download_status=not_exposed_by_public_preview`, `apk_identity_verified=false`. Это **источники объявлений APK**, не доказанная возможность скачивания вложений без Telegram-аутентификации. В этой ветке скачивание байтов Telegram-документов не реализовано; доступный локальный APK принимается отдельной инспекцией. Ссылка `VIEW IN TELEGRAM` не считается скачанным файлом. Возможный внешний публичный APK mirror нужно подтвердить отдельно по происхождению и хешу.

## Артефакт и мост

`inspect_plugin_artifact(path)` читает EAF или standalone Python, проверяет AST без импорта/исполнения, идентичность встроенного и архивного DEX, объявленную контрольную сумму и версию. Объём архива ограничен, дубли имён отклоняются. Отдельные warnings сообщают о `__file__` и `elyx.assets`; наличие текста не доказывает ошибку, отсутствие этих ссылок не доказывает успешную установку. Установка и фактический SDK остаются PENDING.

`probe_bridge_contract()` выдаёт минимальный диагностический `.plugin`. Он должен исполняться через штатный загрузчик целевого клиента, а не на Windows Python. Проверки: Java Class metadata, типизированные int/long/boolean, `notify`, direct dynamic_proxy, before/after-вызов хука на собственном View.setTag и доступность дополнительных методов параметра. Хук снимается в finally. Плагин не читает переписки/настройки и не отправляет сообщения. Наличие дополнительных методов не требуется для успеха; результат показывает, на какие методы нельзя опираться. Возврат исходника сам по себе всегда PENDING. Физический клиент в этой ветке этот новый probe пока не исполнял.

`probe_bridge_contract(report)` оценивает импортированный JSON, но сохраняет `runtime_verified=false`. Требуются отдельные проверки фактического SDK, перезагрузки DEX с независимыми loader и конечной функции. Самостоятельно объявленный PASS не записывается в verified-базу знаний; прежний `record_runtime_result` остаётся закрытым до доверенной аттестации.

`analyze_hook_impact(path,class_name,method,callers)` показывает декларации и ссылки в **явно перечисленных** caller-классах exact APK. Перегрузки сохраняются. Покрытие не объявляется полным call graph; поток и порядок callbacks остаются неизвестными до исполнения. Перед изменением общего getter проверять его использование UI, рекордером и возобновлением записи.

## Диагностика и приёмка

`analyze_run(log,expected_artifact?)` принимает до 64000 UTF-8 байт JSONL, отделяет версии/сессии/задания, сообщает о повреждённых строках и разрывах seq. Сравнивает video/audio maxPtsUs с ожидаемой длительностью, дорожки/размер оригинала и копии, покрытие частей и ACK. Допуск длительности — 1 секунда, технический порог для диагностики, не гарантия качества. Несовпадение времени таймера и исходных пакетов показывает потерю до копирования; оно не определяет виновную инструкцию рекордера.

`verify_feature` возвращает FAIL при установленном противоречии, PENDING при отсутствующих проверках, EVIDENCE_CONSISTENT при согласованности всех данных. `runtime_verified` всегда false: журнал и визуальные наблюдения предоставлены вызывающим, независимой аттестации нет. Пакетные отметки не исключают застывшее изображение/тишину: нужны движение, речь после минуты и непрерывность стыков. Для импорта без аудита исходника нельзя получить полный успех из одного `convert.done`/`queue.done`; этот маршрут остаётся PENDING.

## Остаток полного объёма работ

- Найти и проверить доступ к **байтам** Telegram APK без входа либо согласовать, что каталог объявлений и локальный импорт покрывают требование источников.
- Довести клиентский мост до запуска/проверки точного diagnostic artifact, независимого DEX reload и фактического SDK; сейчас готовится probe, не выполняется на телефоне сервером.
- Добавить полную отдельную приёмку импортированного видео и покрытие галерея/сообщение/камера/fallback, включая правки кадра и звук.
- Независимый review всей итоговой реализации; полные checks и wire-прогон нового набора инструментов.

Эти пункты не считаются завершёнными по наличию новых инструментов или зелёных узких тестов.
