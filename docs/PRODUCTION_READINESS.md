# ExteraContext: release and operational readiness

**Status: release checklist, not a production-ready declaration.** These are controls to verify on the actual deployed version and environment. The local `npm test` suite exercises the official MCP SDK stdio and authenticated Streamable HTTP wire paths against a synthetic SQLite corpus; CI is configured to install locked dependencies, create a synthetic fixture, and run those tests. GitHub CI evidence is recorded per commit in PR #1; use the latest check result rather than treating an older successful run as evidence for new changes. These tests do not validate the approved production corpus, a deployed server/environment, ExteraGram/AyuGram device runtime, benchmark superiority, or a verified repository pin. The protected updater/workflow documented below exists, but has not been run as part of this documentation update; no updater fetch or corpus update is claimed.

## Assets and trust boundaries

- **Immutable base:** `data/exteracontext.sqlite` (override with `EXTERACONTEXT_DB`) is the deployed SQLite knowledge index. Read-only retrieval must not mutate it. Both MCP transports run an offline corpus preflight before serving. A missing/corrupt base, nonempty SQLite sidecars, or an invalid/mismatched deployment manifest blocks startup. Retrieval opens the base with SQLite `mode=ro&immutable=1` and `query_only=ON`. With `EXTERACONTEXT_AUTO_SYNC` unset or `0`, the updater is offline and does not access the network. Only an explicit `EXTERACONTEXT_AUTO_SYNC=1` invokes the trusted, hash-pinned updater; see the protected release workflow below. Avoid deploying a checkout whose local wiki/build path would implicitly build a missing base.
- **Mutable overlay:** `data/knowledge.sqlite` (override with `EXTERACONTEXT_KNOWLEDGE_DB`) holds claims, evidence, verification and audit history. A read-only query with no overlay must not create one; a malformed or incompatible overlay is an error, not an empty store. Initialize it deliberately with `python scripts/knowledge.py init` only where write-back is authorized. Protect its directory from untrusted writers; treat capability tokens and data as sensitive.
- **Transport:** stdio assumes a trusted local MCP host, filesystem and inherited environment, with no transport bearer challenge. HTTP is loopback-only; startup requires `EXTERACONTEXT_MCP_HTTP_TOKEN` of at least 32 UTF-8 bytes, and MCP requests require `Authorization: Bearer <token>`. Keep the token out of argv, URL, logs and repository. Host/Origin validation and CORS are not a substitute for bearer authentication. Proxying beyond loopback needs a separately reviewed authentication and access policy.
- **Write-back:** capability tokens authorize distinct collector/verifier stages; hashed token storage, stage guards and SQLite run-ID guards do not prove **physical verifier independence**. The host must actually isolate independent agents and withhold the candidate until Phase A is persisted. Host-provided runtime actor IDs are caller-attested provenance, not authorization. To prevent token leakage into process argument lists (OS `process.argv` inspection), MCP orchestration invocations transmit capability tokens over `stdin` via `--actor-token-stdin`.
- **Runtime:** the MCP `record_runtime_result` endpoint is disabled/fail-closed until a trusted machine attestation is integrated. The low-level CLI requires matching `EXTERACONTEXT_RUNTIME_SOURCE` / `EXTERACONTEXT_RUNTIME_TOKEN` and `--runtime-source` along with an attestation token for runtime-run creation and result recording. Its implementation tests token length in characters; operational policy must provision an independently generated secret with **at least 32 random bytes** and protect it in a secret manager. To prevent token exposure in process argument inspection (`process.argv`), attestation CLI commands (`run-create --role runtime` and `record-runtime`) support secure token ingestion via `stdin` (`--attestation-token-stdin` or `--attestation-token -`); do not pass raw secrets via argv on shared hosts or expose that path to models or untrusted local users. An attested CLI caller alone does not demonstrate that a device test ran; require independently captured machine logs and exact target/build/device binding.

## Offline bootstrap of an existing corpus

1. Identify a previously approved, quiescent **existing** SQLite source DB; confirm its owner, origin, and permission to deploy. Checkpoint/stop its writer and reject nonempty `-wal`/`-shm`/`-journal` sidecars; never treat an immutable read that ignores a live WAL as complete. Make a restorable backup of both existing destination DB and overlay (including a consistent SQLite snapshot/WAL checkpoint), plus the existing manifest. Record destination paths, permissions, timestamps, source identity and hashes outside the live directory.
2. Run `python scripts/sync_knowledge.py --source <approved-existing.sqlite> --db data/exteracontext.sqlite` from the repository root (or choose an explicit destination). This is an offline copy, not a fetch, git checkout or rebuild. The script checks source integrity, foreign keys, required tables/FTS and nonempty docs/facts, compares SHA-256 before/after copying, and atomically replaces the destination and `data/.knowledge-manifest.json`. Plan downtime/quiescence across replacement: DB and manifest are **two distinct replacements**, not one transaction; verify both together before restarting readers.
3. Inspect `data/.knowledge-manifest.json`: `method: offline-existing-db-copy`, matching `source_sha256`/`destination_sha256`, expected size/schema/counts, and `commit_verified: false`. Recompute/compare the live DB SHA-256 with the manifest and approved source. **The Knowledge commit pin is unverifiable from an existing DB copy**; a hash proves byte identity to that source, not repository-commit authenticity or signed corpus provenance. Do not relabel it as verified. Record this release exception or block release if commit/signed provenance is mandatory.
4. Ensure both DB paths refer to the intended base/overlay and keep `EXTERACONTEXT_AUTO_SYNC` unset or set to `0` for offline operation. Explicit `=1` permits network download only through the trusted updater described below; do not enable it until `KNOWLEDGE_LOCK` contains verified artifact hashes. Protect the immutable base against service-account writes where feasible, keep overlay writable only to the intended service role, and record owner, mode/ACL and retention policy. Do not point base and overlay at the same file.

## Protected hash-pinned update path

The opt-in runtime updater is `scripts/update_knowledge.py`. `EXTERACONTEXT_AUTO_SYNC` unset or `0` is offline/no-network; only explicit `EXTERACONTEXT_AUTO_SYNC=1` invokes it. It is restricted to downloading the `exteracontext.sqlite` and `manifest.json` release assets from the fixed repository `RObotiaga/ExteraContext-MCP`. Before staging deployment, it verifies the tracked lock's database and manifest SHA-256 pins, release identity, manifest source commit, database schema and counts, and SQLite integrity. It does not clone the Knowledge repository or execute its code. Hash pins ensure byte integrity against the reviewed lock, but do not independently establish trust in GitHub, TLS, repository administration, workflow permissions or reviewers. Before replacement, staged DB/manifest files inherit mode, timestamps and supported extended attributes from existing regular destinations. Backup and rollback copies retain source permission bits, timestamps and metadata supported by `shutil.copystat`; POSIX owner/group are preserved, and the updater refuses to replace live files if ownership cannot be retained. On Windows, file attributes are preserved and replacement files inherit ACLs from the destination parent through the same-parent staging directory. Windows per-file explicit ACLs are not copied by this mechanism: deployments using them require operator validation of the resulting ACLs before enabling updates; do not assume full ACL preservation.

`.github/workflows/sync-knowledge.yml` checks the exact `main` commit of `RObotiaga/ExteraContext-Knowledge` on a daily schedule (or manual dispatch), builds a candidate inside an unprivileged, read-only, networkless container, and runs all Python, regression, benchmark-validation and MCP test suites against it. The workflow then waits at the protected GitHub Actions environment `knowledge-publish`; a repository administrator must configure that environment with a required reviewer. After approval, it publishes immutable-by-hash per-commit release assets and opens a pull request to `develop` updating `KNOWLEDGE_LOCK`; it does not push directly to `main`. The lock is usable only after that PR is reviewed and merged and matching release assets exist. GitHub Actions runner operations still require network for checkout, package installation and Actions artifact/release services; the candidate build container itself is explicitly networkless. Do not describe the workflow as executed unless there is a recorded run and result. It has not been run, and no updater fetch was executed, as part of this documentation task.

**Schedule and publication gate:** GitHub scheduled workflows execute from the repository's default branch. This Knowledge workflow has schedule/manual-dispatch triggers only; merging into non-default `develop` or pushing a feature branch does not run Knowledge maintenance. Check the default branch before promotion. At the PR stage, the GitHub API reported `develop` unprotected and zero environments. Before enabling publication, an administrator must configure `knowledge-publish` required reviewers and deployment branch restrictions, plus appropriate branch protection/rules; the YAML does not establish these protections.

**Current lock limitation:** `KNOWLEDGE_LOCK` currently contains only a bare legacy commit SHA, not the complete version-1 artifact lock with asset hashes. The updater deliberately fails closed for this value until a candidate passes the protected publication workflow, is represented by a reviewed/merged lock PR, and its per-commit release assets are available. Thus `EXTERACONTEXT_AUTO_SYNC=1` is not currently a usable update path; leave it unset/0 until the first publication has completed.

## Process startup and service-readiness gates (record actual results, do not assume)

Process/transport startup is not proof of production readiness. The MCP entry point runs `python scripts/query.py preflight` before serving either transport. Preflight validates SQLite integrity/schema and, when present, the paired `.knowledge-manifest.json` hash, size and schema/counts. `EXTERACONTEXT_REQUIRE_MANIFEST=1` also rejects an absent manifest. Unmanaged local fixtures may omit it, but `doctor.corpus_verification.manifest_status` then reports `absent-unverified`. **Deployment status must remain NOT READY until a `doctor` and a representative knowledge query both succeed against the intended deployed database.**

- [ ] Confirm pinned, locally available Node.js 20+, Python 3 and MCP SDK dependencies. Run syntax/contract tests offline; where dependencies are absent, the SDK test **skips** and is not an integration pass. Do not install packages or use network as a hidden verification step.
- [ ] Validate base DB and manifest together, then explicitly run `python scripts/query.py doctor` and `python scripts/query.py api <known-symbol> --format json` against the deployed DB. Both must succeed before marking the deployment ready. Check absent-base behavior blocks startup and is a visible query error and read-only calls do not create the overlay. Test corrupt/incompatible overlay fails visibly. If the source lacks signed provenance, leave this gate recorded as unresolved, not passed.
- [ ] Local `npm test` currently exercises the official SDK stdio and authenticated HTTP wire paths against a synthetic SQLite fixture; CI is configured to install locked dependencies, create the synthetic fixture, and run this suite. Check the latest PR GitHub CI result for the exact deployed code commit. Dependency-absent environments may explicitly skip SDK integration; a skip is not a pass. For release readiness, separately exercise strict stdio (`--modern-only`) and authenticated HTTP with the actual deployed server and approved existing corpus: negotiate `2026-07-28`, list tools, call `doctor` plus representative `find_api`/`search_knowledge`, and check structured responses and UTF-8. Exercise legacy fallback only if supported clients require it. Synthetic-fixture wire success does not validate the approved corpus or deployed environment; transport negotiation/tool listing alone is not readiness.
- [ ] For HTTP, use a protected fresh 32-byte-or-longer bearer, loopback bind and an approved client. Verify startup rejects missing/short env token and public bind; unauthenticated/incorrect bearer returns 401, valid bearer negotiates MCP and accesses a read tool; invalid Host/Origin is rejected. Check OPTIONS behavior separately (preflight is not an authenticated MCP call). A test harness that starts HTTP without supplying the required token must be corrected before its result can be used as release evidence.
- [ ] Verify unauthorized/model-supplied `record_runtime_result` fails closed, fake `runtime-verified` collector/Phase-A submissions fail, and CLI runtime creation/result without attestation fails. Ensure stdin token passing (`--attestation-token-stdin` or `--attestation-token -`) is used rather than argv on multi-user hosts. An acceptance test of guards is **not** a device test.
- [ ] For write-back, test isolated collector/verifier sessions, blind Phase A persisted before candidate disclosure, token replay/wrong-role refusal and SQLite promotion guards using temporary fixtures. Document whether physical process/provider independence can be independently attested; otherwise leave that acceptance item open.
- [ ] Verify restoration from backed-up base, manifest and overlay on a disposable instance, including process startup, `doctor`, representative query and audit-history checks. The MCP process enforces base/manifest consistency at startup; strict deployments must set `EXTERACONTEXT_REQUIRE_MANIFEST=1`. Still record operator provenance/restoration checks and keep deployment NOT READY until the readiness queries succeed.

## Deployment, rollback and operations

The hash-pinned updater attempts to restore the previous DB/manifest pair after a replacement failure. If rollback itself fails, it retains the same-parent `.knowledge-release-*` recovery directory and reports its absolute path in the error. Stop service/writers, preserve that directory privately, and restore `previous-database` and `previous-manifest` together (when those files existed before deployment). Do not delete recovery files or restart service until pair integrity and readiness checks pass. Ordinary successful deployment, rejected validation, and successful rollback remove their staging directories; an interrupted process may also leave staging that needs operator inspection.

1. Stage approved existing corpus, manifest, code/runtime and secrets on a non-production instance; record artifact hashes, pinned package versions, operator, change ticket, test outputs and outstanding exceptions. Keep base, manifest and overlay backups private, encrypted and restorable. Separate writable overlay and secrets from read-only corpus deployment.
2. Stop/quiesce service and overlay writers, back up consistent SQLite snapshots and manifests, perform offline bootstrap, verify copied hash and DB/manifest consistency, then start stdio/loopback HTTP under least-privilege identity. Process/transport startup alone does not mean the corpus service is ready: require successful `doctor` and representative query checks before admitting traffic. Do not publish the HTTP port or reuse an example token. Check both positive and negative startup/auth cases.
3. Monitor operational signals: startup failures, base/manifest hash mismatch, query latency and error rate, bridge timeouts/queue saturation/output-limit errors, HTTP 401/invalid Host/Origin counts, overlay disk growth and WAL/checkpoint age, failed token/replay or promotion checks, backup age and restoration-test date. Alert on sudden changes and protect logs from secrets/evidence leakage. Define local SLO thresholds, owners, retention, and incident routing before rollout; no empirical baseline is asserted here.
4. Rollback: stop service and writers; restore the **paired** known-good base DB + manifest and a consistent overlay snapshot (or keep append-only overlay isolated if schema/data rollback is unsafe), verify hashes/integrity/schema, restart against old artifact, and repeat startup/auth/read checks. Preserve failed artifacts/logs privately for investigation. Do not silently discard newer overlay claims or assume down-migration works. Revoke/rotate exposed HTTP/runtime/capability secrets and document the incident when needed.

## Unresolved release decisions

- **Commit pin / signed provenance:** offline source copy has `commit_verified: false`; no independently validated signed corpus chain is established by these checks. Release owners must accept and document the origin risk or obtain separate approved provenance evidence.
- **Physical verifier independence:** capability continuity and distinct run IDs are logical controls, not host-level isolation evidence. Independently attest separate verifier execution and candidate blinding before claiming physical independence.
- **Runtime CLI argv secrets:** secure stdin token ingestion (`--attestation-token-stdin` or `--attestation-token -`) is now supported to eliminate process inspection / argv interception risks; operational policy must still enforce machine-only access before shared-host operation, as existing character-count checks alone do not establish 32 random bytes of entropy.
- **A/B/C evaluation:** no completed reproducible A/B/C comparison is established here. Do not claim relative agent performance or superiority without preregistered tasks, baselines, scoring, provenance and reported uncertainty.
- **Production-corpus/deployed-server/device validation:** local SDK wire tests pass against a synthetic SQLite corpus, and CI is configured to run the locked-dependency suite with a synthetic fixture; GitHub CI results are tracked separately per commit in PR #1. These results do not validate the approved production corpus or deployed environment. Complete and record the production-corpus/deployed-server checks above and named-build/device runtime checks before making claims that depend on them. If dependencies are missing, an explicit SDK-test skip is not a pass.
